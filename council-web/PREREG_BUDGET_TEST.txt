# Pre-registration: does the file total run above the declared spend by the size of the flagged repeats?

Written 2026-10-03 (Session 29) BEFORE any confirmatory number is computed. Committed to git before the run so the
commit time proves the order. Nothing outward is involved: all comparators are public statistics (Open Government Licence)
and the councils' own published files.

## The question (owner, 2026-10-03)
"Whether the anomalies actually add up to the total number. Somewhat proving that duplicate payments happened."
If a council's over-GBP500 file total runs ABOVE what the council declares it spent, by roughly the size of the repeats and
twins we flag, that supports "these were real extra outgoings (or real errors in the published record)". If it does not, the
flagged rows are more likely presentation artefacts, or the comparison cannot tell.

## What I looked at before writing this (disclosure)
While planning I printed ONE unit: Wokingham FY2023-24, file Net GBP 260.2m against Revenue Outturn running expenses
GBP 220.0m (employees GBP 151.9m, total gross service expenditure GBP 371.9m). That unit is EXPLORATORY and is excluded from the
confirmatory pool below. I have not looked at any other council's comparator. I have not computed any residual R or flagged
total T for any unit.

## Units
A unit is a council x financial year (1 April to 31 March) with: (i) published rows whose PayDate covers all twelve months
(each month holding at least 50% of that council's median month; a month missing or mostly empty excludes the unit), and
(ii) published Revenue Outturn (RSX/RO) for that year. Years considered: 2022-23, 2023-24, 2024-25 (2025-26 is first-release
and our files stop at Dec 2025). The pool is every unit that meets this rule across every council in the repository when the
run is made; no unit is dropped or added because of how it looks. The pool is written to `export/budget_units.csv` before
any residual is computed and is not edited afterwards. Calendar-year councils (Merton) are cut by PayDate, not by file tag.

## Quantities per unit (all GBP, from the engine's own export, retained AND redacted rows that carry an amount)
- F = sum of published Net over the unit's rows, each published row counted once (overlap and republished files removed by the
  existing engine rules; files flagged `FileDuplication` are counted as published, because F is "what the file says").
- K1 = Revenue Outturn running expenses (C2), all services, plus Housing Revenue Account total expenditure where RO4 gives one.
  Employees (C1) are NOT in K: payroll is not paid through the supplier ledger.
- K2 = K1 + Capital Outturn Return total capital expenditure for that council and year.
- K3 = K2 + OBSERVED pass-through and payroll-liability payments found in the file by payee-name rule, fixed now:
  payee contains "REVENUE & CUSTOMS" or "HMRC"; "PENSION"; "POLICE" with "CRIME COMMISSIONER" or "THAMES VALLEY POLICE"-style
  police authority names; "FIRE" with "RESCUE" or "AUTHORITY"; "PARISH COUNCIL"; "TOWN COUNCIL". (These sit in the file but
  not in revenue running expenses or capital; adding them removes them from the gap by name. Each is shown as its own line.)
- R = F - K. Positive R means the file is above the comparator.
- T_A ("published twice" tier) = value of the SECOND and later copies of: (a) transaction twins (`transaction_twins.csv`, kind
  "identical in every published column except the transaction number" or "one payment, repeated lines"), (b) internally doubled
  transactions (every line listed an even number of times), (c) exact repeated rows inside a file flagged by `FileDuplication`.
- T_B ("repeat-payment leads" tier) = T_A + value of the second and later rows of every Schedule B group classed Unclear or
  StandingScheduleSurplus (excess copies only, never the first). T_B is large and mostly legitimate recurring payments; it is
  the upper bracket, not a claim.
- Ratios: r = R / F and t = T / F, so that size of council does not drive the result.

## Arms (A/B/C/D) and declared search width
Comparator definitions: 3 (K1, K2, K3). Flag tiers: 2 (T_A, T_B). That is 6 combinations; ALL SIX are reported, none is chosen
afterwards. The primary, fixed now, is K3 with T_A. Table to be filled in the report:

| Arm | Comparator | Flags | Role |
|---|---|---|---|
| A | K3 | T_A | PRIMARY |
| B | K3 | T_B | broad bracket |
| C | K2 | T_A | no observed pass-through (checks K3 did not manufacture the answer) |
| D | K1 | T_A | RO only (checks capital added nothing artificial) |
(K1/T_B, K2/T_B reported as extras, not arms.)

## Statistic and decision rule (primary arm and each other)
Fit r = beta * t through the origin across units; bootstrap the units 10,000 times for a 95% interval on beta.
- Null 1 (no relation): beta = 0. Rejected if the interval excludes 0.
- Null 2 (chance baseline): permute t across units 10,000 times (each unit gets another unit's t) and refit; the real beta must
  exceed the 97.5th percentile of the permuted betas. This is the baseline for the scale of the comparator noise.
- Calibration (the power rule): define N = median absolute deviation of r across units. If the median t is below N the test
  cannot discriminate and the verdict is INCONCLUSIVE whatever beta says.
Verdicts, in order:
 1. INCONCLUSIVE if median t < N, or the interval contains both 0 and 1.
 2. SUPPORTED (flagged rows behave like real extra outgoings or real record errors) if the interval excludes 0, contains 1, and
    beta exceeds the permutation 97.5th percentile.
 3. NOT SUPPORTED (flagged rows behave like presentation artefacts) if the interval excludes 1 and contains 0 and median t >= N.
 4. Anything else (interval excludes both): reported as an unexpected shape with the numbers, no verdict.
I expect INCONCLUSIVE for the broad tier because the comparators are only accurate to a few percent of a council's total and
payments under GBP500, card spend and capital timing sit on the same scale as the flags; if that happens it is the honest result.

## Per-unit arithmetic shown publicly (`export/budget_reconciliation.csv`)
For each unit: the declared figures (employees C1, running expenses C2, total gross C3, HRA, capital), the file total F, each
observed pass-through line by name, the residual R, the flagged totals T_A and T_B, and what is left (R - T_A) labelled
"unexplained". Every line carries a Source (RSX/RO/COR file and year) and a Kind (declared, observed in file, flagged by rule,
unexplained).

## What this can and cannot prove (stated before the result)
- The published files cannot show which bank payments left. A positive R equal to T would be consistent with real extra
  outgoings OR with the same rows being published twice in the record; the comparison cannot separate those two.
- Revenue Outturn is revenue only and net of recoverable VAT; the file is gross of payment, includes capital, pass-through,
  loan principal, treasury movements and credit notes. Items I cannot name (payments under GBP500, card spend, payroll, school
  bank accounts, non-cash charges) stay in "unexplained" and are not allocated.
- A positive result for the pooled slope does not prove any one flagged payment was duplicated.
